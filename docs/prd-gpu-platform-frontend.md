## 问题陈述

GPU 平台当前已经具备仪表盘、沙箱、批量任务、模型、数据集、文件和管理中心等前端原型页面，但整体仍以静态展示和前端模拟交互为主，尚未形成完整、可解释、可联动的产品体验。

从用户视角看，当前最主要的问题集中在三个方面：

1. 任务排队不透明。用户提交任务后，不清楚还要等待多久，也难以判断当前提交是否合理。
2. 高优先级任务抢不到资源。团队负责人无法直观看到是谁占用了资源，以及为什么当前资源不能让渡给更重要的任务。
3. GPU 利用率低。用户缺少统一的资源使用视角和配置约束，平台也缺少清晰的配置入口来管理优先级、配额和 GPU 使用边界。

本次 PRD 的目标不是设计后端调度系统，而是整理并定义 GPU 平台的前端交互方案，使算法工程师、团队负责人和管理员能够在统一产品界面中完成任务提交、状态查看、资源洞察、资源入口联动和策略配置。

## 解决方案

构建一套面向完整 GPU 平台的前端交互方案，覆盖批任务、沙箱、模型、数据集、文件和管理中心，但聚焦于“交互闭环”和“信息表达”，不展开后端实现方案。

方案重点包括：

1. 统一任务创建与配置体验，明确必填字段、高级选项、默认值和表单约束，减少任务提交歧义。
2. 在任务与沙箱状态展示中补齐前端产品表达，重点加入预计排队时间、任务生命周期状态、运行结果和角色差异化可见信息。
3. 为团队负责人提供团队视角的 GPU 占用、排队成员、成本与利用率概览，并展示资源占用者及不能让渡的原因。
4. 建立模型、数据集、文件和任务之间的入口联动与产物关联，让各模块不再孤立。
5. 将管理中心定义为配置页，突出团队优先级、配额、GPU 白名单和相关平台策略设置。
6. 明确角色权限视图，区分算法工程师、团队负责人和管理员在信息可见性与操作能力上的差异。

5. 作为算法工程师，我希望任务创建表单提供校验和约束提示，这样我可以及时发现配置是否缺失或不合法。

## 实现决策

- 本 PRD 仅覆盖前端交互方案，不展开后端调度、集群编排、服务架构或调度器实现设计。
- 产品范围覆盖完整 GPU 平台前端，包括仪表盘、沙箱、批量任务、模型、数据集、文件和管理中心。
- 沙箱与批量任务在首版中保持为两条独立工作流。它们可以共享视觉语言和部分配置概念，但不被定义为可互相转换的一体化流程。
- 批量任务创建采用结构化配置模型，必须明确区分必填字段与高级选项。
- 任务创建的必填字段为：镜像、启动命令、GPU 卡型、GPU 卡数、CPU、内存。
- 任务创建的高级选项为：数据集、环境变量、优先级、重试策略。
- 多节点训练与 Gang scheduling 在首版中不作为表单主路径重点突出，只允许在状态解释或任务说明中被轻量表达。
- 任务生命周期在界面上必须支持 draft、queued、scheduling、running、succeeded、failed、cancelled 和 preempted。
- 面向普通用户的排队透明度在首版中仅展示“预计排队时间”，不展示底层调度原因。
- 团队负责人视图中的排队解释比普通用户视图更丰富，可以看到当前是谁占用了资源，以及为什么这些资源不能让渡。
- 仪表盘与任务视图应区分个人操作视角与团队管理视角，而不是将所有维度信息堆叠在同一界面中。
- 团队资源洞察视图必须覆盖团队 GPU 占用、排队成员、成本、利用率，以及团队负责人做管理决策所需的补充解释信息。
- 管理中心的产品定位是配置页，而不是实时控制塔。它用于管理策略和访问约束，而不是承载实时调度指挥。
- 管理中心必须支持团队优先级、配额和 GPU 白名单等配置能力，同时承载相关平台策略设置。
- 模型、数据集、文件与任务之间的入口联动属于核心产品能力，而不是附属快捷操作。
- 模型页必须支持直接发起沙箱和训练任务。
- 数据集页必须支持直接发起沙箱和训练任务。
- 文件管理必须支持将 checkpoint 类产物发布到模型模块。
- 训练完成后，界面必须能表达任务、文件产物和模型资产之间的关联关系。
- 角色权限与可见性是首版必需的产品概念，至少要区分算法工程师、团队负责人和管理员三类视图与能力边界。
- 首版产品不将“推荐/建议”作为核心交互能力，不在创建、排队和失败场景中强调主动建议式体验。
- 前端产品架构应优先围绕以下深模块组织：
- 一个任务创建与配置模块，封装字段分组、默认值、校验规则和可提交状态。
- 一个任务状态与排队可视化模块，统一管理生命周期展示、预计排队时间和状态解释规则。
- 一个团队资源洞察模块，负责团队 GPU 占用、排队成员、成本、利用率以及团队负责人可见的资源解释信息。
- 一个资源入口联动模块，负责模型、数据集、文件和任务之间的跳转入口、产物关系和上下文继承。
- 一个管理中心配置模块，负责平台策略、团队优先级、配额和 GPU 白名单等配置能力。
- 一个权限与角色可见性模块，负责不同角色下的信息显示范围和操作能力约束。

## 测试决策

- 好的测试应当验证用户可见的外部行为，而不是验证组件内部实现细节、临时状态结构或 Hook 的实现方式。
- 好的测试应当聚焦用户能够看到什么、能够配置什么、能够提交什么，以及在什么条件下被阻止操作。
- 最高优先级的测试模块是任务创建与配置模块。
- 任务创建相关测试应覆盖必填字段与高级选项的分组展示、表单校验、提交可用性以及字段可见性规则。
- 任务创建相关测试应验证：缺失必填字段时不能提交，而高级选项保持可选。
- 任务创建相关测试应验证：批量任务与沙箱创建流程在交互层面保持清晰分离。
- 第二优先级的测试模块是管理中心配置模块。
- 管理中心配置测试应覆盖角色权限控制、配置项编辑行为，以及团队优先级、配额、GPU 白名单等关键配置项的可见性与可操作性。
- 管理中心配置测试应验证：非管理员角色不应看到或不应能够操作受保护的配置能力。
- 当前仓库中尚未看到既有自动化测试文件或成体系的测试先例，因此本 PRD 无法引用代码库内现成的测试 prior art。
- 当后续开始补充测试时，应统一采用产品契约驱动方式，围绕页面展示、用户操作、拦截条件和角色差异进行验证。

## 不在范围内

- 后端调度系统设计
- 集群编排与底层资源分配实现
- 调度器、队列系统或产物服务的 API 设计
- 实时控制塔或运维大屏类产品形态
- 推荐系统或主动建议式交互能力
- 多节点训练或 Gang scheduling 的一等配置工作流
- 将沙箱和批量任务合并为单一工作流
- 超出前端产品表达需求的基础设施观测能力设计

## 补充说明

- 当前仓库已经具备较完整的前端原型页面，因此这份 PRD 的价值不在于重新定义模块名称，而在于明确行为边界、角色边界和模块联动方式。
- 现有 UI 已经覆盖了大量静态展示和前端模拟提交场景，后续可以基于这份 PRD 逐步将各页面升级为统一、连贯的真实产品交互。
- 这份 PRD 适合作为后续前端需求拆分的基础，尤其适用于任务创建复杂度控制、排队透明度表达、团队资源管理和跨模块资产流转等方向。
